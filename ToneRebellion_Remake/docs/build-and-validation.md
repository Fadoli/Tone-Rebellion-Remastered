# Build and validation

An independent, modern C implementation informed by the static analysis documented in the parent `FLOAT_decompilation` directory. Original game files are read-only reference data; the remake does not launch `FLOAT.EXE` or write to the original installation.

## Current milestone

The current implementation contains a portable C11 reader for the observed COB archive directory, parsers for the world map, island locations and construction catalog, an SHP RLE decoder, and a Windows menu executable. The COB API opens archives read-only, validates the fixed-width directory and member ranges, lists entries, and reads a selected member into caller-owned memory. The world parser accepts either an extracted `worldpos.txt` or `data\\worldpos.txt` directly from a COB. Two desktop shells share the game code: `remake_menu` (Win32/GDI) and `remake_sdl` (SDL3 window, events and presentation; audio through SDL; TCP sockets through `src/platform/net_socket.c`, Winsock on Windows), see [SDL3 build](#sdl3-build).

Build with CMake and a C11 compiler. `remake_inspect_cob <archive.cob>` lists archive entries. Run `remake_inspect_worlds <path-to-WORLDPOS.TXT>` for an extracted table, or `remake_inspect_worlds --cob <archive.cob> data\\worldpos.txt` to read the member without extracting or modifying the archive. On Windows, the ready-to-launch executable is `ToneRebellion_Remake.exe` in this directory; it reads the original data read-only and needs no installation: `--game-dir <path>`, `TONE_REBELLION_GAME_DIR`, the executable folder (or its `THING1`), `C:Program FilesTone`, `THING1` of any drive (mounted ISO) and `C:	oneIsoTHING1` are tried in that order, first folder containing `TONE01.COB` wins. Music is read from the sibling `THING2`. A disc image works directly too: drag the `.iso` (or a game folder) onto `ToneRebellion_Remake.exe`, or use `--iso <file.iso>`, `TONE_REBELLION_ISO`, an ISO next to the executable, or `C:\TONE116F.ISO` (last resort). `src/data/iso9660.c` reads the image read-only (cooked 2048 or raw 2352 sectors) and copies the needed files once into `%LOCALAPPDATA%\ToneRebellion_Remake\iso_cache`; tunes are copied on first play.

## SDL3 build

MSYS2 (`C:msys64`, UCRT64 shell) provides GCC, CMake, Ninja and SDL3:
`pacman -S mingw-w64-ucrt-x86_64-{gcc,sdl3,cmake,ninja,pkgconf}`. From a UCRT64 shell:

```sh
cmake -S . -B build/ucrt64 -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build/ucrt64
```

This builds the game `remake_sdl` (SDL3 is required, and OpenGL 3.3 for the scaling filters; the shaders under `shaders/` are embedded by `python tools/embed_shaders.py` into the committed `src/platform/sdl/sdl_gl_shaders.h`, to rerun after changing a shader; the Win32/GDI `remake_menu` build was dropped on 2026-11-06). Each build also refreshes the ready-to-launch copy in `ToneRebellion_Remake/`: `ToneRebellion_Remake.exe` with `SDL3.dll` and the `libiconv-2.dll` it imports (without that copy Windows would load another libiconv from PATH, such as Git's, which breaks SDL's UTF-16 conversions). The executable needs only system DLLs otherwise. The 32-bit MinGW.org build keeps working; 32-bit GCC builds use SSE math (`-msse2 -mfpmath=sse`) so every build places float-computed pixels identically. Remake saves go to `saves` beside each executable. `remake_sdl` embeds a manifest (`src/platform/sdl/utf8.manifest`) that sets the process code page to UTF-8 (Windows 10 1903+), so `fopen` accepts the UTF-8 paths SDL returns, for example a game folder named `Tône`.

## Web build

From a UCRT64 shell with `mingw-w64-ucrt-x86_64-emscripten`: `tools/build_web.sh <SDL3 source directory>` builds SDL3 for Emscripten once (`build/web/sdl3`), then the game (`build/web/game`, or a second argument), and copies the page, script and wasm to `web/out/` (ignored by git). Later builds can pass `""` as the source directory. The script sets `BINARYEN_CORES=1`: with its default thread pool `wasm-opt` deadlocked during the link. Serve `web/out` as static files; the page asks for the game folder or the CD image (`.iso`, ISO 9660, read by slices), or `?data=<url>` fetches the same `THING1/`/`THING2/` layout from a URL.

## Build status

Built successfully with CMake and MinGW GCC 6.3.0. On Windows, the `remake_sdl` post-build step refreshes the root `ToneRebellion_Remake.exe` from the just-built target. The e2e scripts drive it with posted window messages: with `TONE_REBELLION_E2E_STATE` set, `src/platform/sdl/e2e_input_win.c` hands posted mouse and key messages straight to the game (SDL drops posted mouse buttons). The COB lister reads 21 entries from `TONE00.COB` and 462 from `TONE01.COB`. The world parser reads `worldpos.txt` both from the local corpus and directly from `TONE01.COB`; counts are `(7, 8)`, `(11, 14)`, and `(15, 22)` for worlds/islands/links. The island parser represents the eleven location tags accepted by original `FUN_00461b3b`, preserving their renderer class/subtype/variant fields. Unknown tags are preserved verbatim and use the fallback site renderer so a new tag cannot prevent opening the whole island. Tone locations are handled as a distinct entity: `POOL` maps to `data\\tone.shp` (40 frames) and declares `CHUG 2 40 3 P` in local `bldinf.txt`; the pool frame mapping follows `FUN_0040bf98`, and runtime items 0 and 5 use their distinct per-record CHUG counter progressions from `FUN_00450a71`; only the wall-clock cadence remains a 33 ms UI-timer approximation. POOL has no PADS-only world-x phase. The explicit `smpad`, `mdpad`, and `lgpad` tags use the 27-frame `PAD.SHP` asset in three nine-frame groups; their phase follows the PADS-specific `FUN_0040ab42` path. `levshld` is not misrendered as a small pad because its specific `SPEARS.SHP` frame mapping remains unresolved. Class-2 bridge sites draw the `BR-TRG01.SHP` base frame; this follows the class-2 `PIT_BridgeTrigger` row in `pad.txt` and its `BR-TRG01` shape, with `bldinf.txt` specifying base frame 1. The 33 ms window timer approximates the original game tick; tribe-visibility flags remain unresolved. The island surface also loads each island's `Ixx-FEAT.SHP` and draws the static feature-sheet layers according to `FUN_0040b345` and each site's `special_value`; triggered layers and altitude haze still need live simulation state. Location layers use the original ascending-Y comparator `FUN_00432940`. Both HZT lookup banks are reconstructed and loaded with the island palette, but scene haze has not been applied to sprites. The `PIT_Object` catalog row has no base building SHP, but generated runtime item 1 now draws its collectible overlay from `alltrigs.shp` using the `+0x24` shape selector. Class-3 `PIT_FeatureTrigger` remains omitted because its row is `noshape`; remaining `special` sites still use inspection markers. `FLOAT.EXE` has not been run.

Regression checks: `ctest --test-dir build --output-on-failure` runs the unit tests, including original RNG, runtime item-rendering, and floater-motion checks. `test_game_session_schema` checks that `src/core/game_session_schema.c` describes every byte of `GameSession` and the structs it contains (remake saves store that table and load by field name): after a field change, regenerate it with `python tools/gen_session_schema.py . > src/core/game_session_schema.c`. If Node.js is available at configure time, CTest also checks Markdown UTF-8/encoding markers, local links, and `FUN_*` references against `decompilation/index.jsonl`. `build/test_curved_text_layout.exe <BGOUTFNT.FNT> <newgame.txt>` checks all eight original tribe paragraphs; `build/test_curved_text_layout.exe --archives <TONE00.COB> <TONE01.COB>` checks the exact archive-loading path used at startup. `build/test_pad_catalog.exe <original_content_dir>\\pad.txt` also validates the complete 101-record catalog, original item ordering, and four 16-item player-tribe blocks. `build/test_island_corpus.exe <original_content_dir>` parses every extracted `ISLANDnn.TXT`; `build/test_island_cob.exe <TONE01.COB> <original_content_dir>` parses all island text members and decodes every frame of the SHP assets listed by the local `shapes.txt` manifest, comparing asset paths case-insensitively as Windows does. Non-manifest `.SHP` placeholders such as `l-magton.shp` are excluded. The SHP decoder bounds a frame by its next distinct offset, so shared frame offsets are supported; header-only frames are transparent. Tests also verify that `tone` remains distinct from `PAD_SMALL`, that `TONE.SHP` has 40 frames, that the POOL preview ping-pongs over its locally declared CHUG range, that runtime items draw BASE and follow CHUG loop/ping-pong timing, and that each starting hall SHP has the frame count required by its `BASE` range. CTest targets keep assertions enabled in Release builds.

Tone-pool rendering is layered: `FUN_0040bf98` draws the static `BASE 1 1` frame first, then the animated `CHUG 2 40 3 P` layer from `bldinf.txt`. The remake composites both frames from `tone.shp`. `FUN_00450a71` gives class-1 runtime ID 0 the counter loop 0..89→0, and ID 5 the distinct 0..125→102 loop; the renderer maps each through `FUN_0040ab05` at speed 3. These are two tracks over the same asset and descriptor, not two separate SHP resources. `POOL` has no `world_x % 23` phase; that belongs to `PADS`'s `FUN_0040ab42`. The island view retains the original runtime-ID gate for POOL fields; placed items stay limited to construction sites, with an exception to draw an already-present Leviathan building on a Tone site where it replaces the POOL art. The 33 ms window timer still substitutes for the original game tick cadence.

## End-to-end UI smoke test

The e2e scripts need the developer shortcuts, which only debug builds have: they run `build/debug/remake_sdl.exe` (`cmake -S . -B build/debug -G Ninja -DCMAKE_BUILD_TYPE=Debug`, then `cmake --build build/debug --target remake_sdl`; `-Exe` picks another build made with `-DTONE_REBELLION_DEBUG_KEYS=ON`). A build with these keys does not replace `ToneRebellion_Remake.exe`.

`powershell -ExecutionPolicy Bypass -File tests/e2e/island_e2e.ps1` launches the debug build with `TONE_REBELLION_E2E_STATE` pointing at a snapshot file, drives the real window with posted mouse/keyboard messages and asserts on that snapshot (`src/platform/win32/menu_app_sections/e2e_state.inc`: screen, island, scroll, selection, panel mode, Hall default, floaters, locations, shortcut slots) and on `PrintWindow` captures saved under `%TEMP%
emake_e2e`. It starts from the static `enemy_hall` fixture (below) with saves and settings in a temporary folder, so no player save is needed or touched. Test-only variables for static fixtures: `TONE_REBELLION_SAVE_DIR` moves every remake save, `resume.gam` and the `.cfg` files to another folder (the player's `saves` is then never read or written); `TONE_REBELLION_E2E_LOAD` names an original `.SAV` loaded at startup with a fixed seed, and `TONE_REBELLION_E2E_ISLAND` the island to open (both only with `TONE_REBELLION_E2E_STATE`). The ISO's `THING1\*.SAV` are 1-byte placeholders, not usable fixtures.

`powershell -ExecutionPolicy Bypass -File tests/e2e/fixture_e2e.ps1` needs no save: `TONE_REBELLION_E2E_FIXTURE=badges` builds a static game (world 0, tribe 0, difficulty 0, fixed seed, as the bench) and adds known units beside the Hall (own warrior subtype 4 at full charge, an enemy subtype-1 unit, Leviathans of subtypes 12 and 9 further away; `e2e_build_fixture`, `native_save_add_fixture_floater`). Saves and settings go to a temporary folder. Checked: the island opens, the three units exist, clicking the warrior selects it, and with `TONE_REBELLION_E2E_FIXTURE=enemy_hall` (same game, tribe 1's Hall island opened, one built bridge out of each Hall island) and `TONE_REBELLION_E2E_SELECT=<site>` (its workers stand on it, so it is selected at startup rather than clicked) that Hall draws `NEWGAME1` in IWTextInfo (state line `text_info`). With `TONE_REBELLION_E2E_FIXTURE=spell` (a stocked 0x2f building near the Hall with a linked level-1 caster, selected at startup) BC_Spell7 (kind 14, no target pick) starts a cast effect that ends after its animation (state line `cast_effects`). On the `badges` game the subtype-12 Leviathan is clicked and selected (it spawns inside the Hall island's floater range; that island does not scroll). With `obtain` (a PIT_Object holding artifact 6 on the nearest empty pad to the Hall, selected) BC_Obtain sends a worker that picks it up (floater line `cargo`). `dying` kills the enemy unit at startup to show the death cells. With `victory` (the last island's seals removed, speed 3) the end sequence starts, returns to the map and opens the end screen (state lines `sequence`, `sequence_tick`). On the obtain game, an empty buildable pad opens IWConstruct and hovering its first column fills IWConstructInfo (state lines `construct_open`, `construct_column`, `construct_item`; the script moves the real cursor there, since a posted move alone is followed by WM_MOUSELEAVE). Captures of the world badges (after TOGREALM), the warrior panel and the enemy Hall are saved for inspection.
